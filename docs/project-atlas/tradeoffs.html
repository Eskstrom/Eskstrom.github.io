Engineering judgment / 30 September 2026

Vector or graph?
Start with the question.

For this portfolio, the graph earns its place by making connections inspectable, not by proving that vector databases retrieve worse answers.

Decision for this release: keep the small, local project graph for browsing and evidence inspection. If natural-language discovery becomes a real need, test dense retrieval alongside lexical search before adding a hosted database. Use hybrid retrieval only if a controlled evaluation justifies the extra complexity.

First, compare the right things.

A vector database is storage and indexing infrastructure. Dense retrieval ranks content using embedding similarity. A graph models entities and relationships; graph retrieval follows selected relationships. RAG adds answer generation on top. These are different layers, not two mutually exclusive products.

Project Atlas today: an offline JSON graph, keyword-derived topic edges, lexical filtering and a browser interface. No vector database, dense embeddings, answer generator or HydraDB query runs in the published map. Its graph is repository → mentioned theme → related repository, not a verified dependency graph or a system that explains architectural decisions.

Modern vector search can apply structured filters; “find public repositories with code” is not uniquely a graph capability. Pinecone, for example, documents filters alongside similarity queries. Source: Pinecone metadata filtering.

Where graphs can earn their complexity

When a task genuinely needs relationships, typed edges can make the retrieval path explicit and constrain which evidence is followed. Examples include a recorded decision, its supporting discussion and a superseding decision. That benefit depends on capturing correct entities, relationships and provenance. Drawing extra connections does not repair missing evidence.

Microsoft’s GraphRAG research investigates graph-based approaches to corpus-level, query-focused summarization. Its reported results concern that method and evaluation setting; they do not validate this keyword-topic map or establish a universal graph advantage. Source: From Local to Global.

The hybrid option

A useful candidate architecture is: apply access and status constraints, retrieve candidate projects through lexical or dense search, then follow a bounded set of supported edges and show the evidence. This can combine flexible discovery with explicit context, but introduces ranking, traversal budgets and more failure modes. Neo4j documents vector, hybrid and graph-augmented retrievers, illustrating that these approaches can be combined rather than chosen exclusively. Source: Neo4j GraphRAG retrievers.

What this release demonstrates

  • A public-only, dated repository inventory with commit-linked source artifacts.
  • Visible topic associations and a distinction between concepts, documentation, forks and code-bearing repositories.
  • Key-free browsing and a reproducible export boundary for private versus public repository records.

Not established: higher retrieval precision or recall than dense search, answer faithfulness, reduced hallucinations, better database performance, temporal correctness, production access control, or HydraDB superiority. Source-code presence is not proof that a product works. Topic labels are automatic and require human review.

The next fair experiment

Freeze one approved corpus and the relevance labels before tuning. Use 20 questions: five exact lookups, five paraphrases, five relationship tasks and five unsupported or out-of-scope questions. An independent reviewer should label required evidence. If Atlas has no decision edges, decision-rationale questions should be scored as unsupported, not assigned invented answers.

  1. Compare metadata/lexical search, dense search with the same filters, the current graph, and a hybrid candidate. Use the same documents and access rules.
  2. Use identical top-k and context-token budgets; test k=1, 3 and 5. Separate node relevance from correctness of the displayed relationship.
  3. Report precision@k, recall@k and ranking quality by question type, plus unsupported-query behavior. At this sample size, publish individual cases and uncertainty rather than a sweeping winner.
  4. Measure cold/warm latency, build/refresh time, resource use and any model costs. These must be observed, not inferred from architecture.
  5. If answer generation is added, hold the generator and prompt constant. Have humans assess answer correctness and claim-to-source support; retrieval coverage alone is not faithfulness.
  6. Run ablations: traversal without special ranking, ranking without traversal, and a larger lexical context. This checks whether an apparent graph gain actually comes from another change.

Adoption rule, not a result: keep the simpler baseline unless the new method materially improves the target task at an acceptable cost. Predefine that threshold and an allowed regression budget before running the comparison.

This is an implementation analysis and proposed evaluation, not a completed dense-vector benchmark. Technical references were checked on 30 September 2026. The recommendations are engineering judgments for this small portfolio use case, not vendor performance claims.
